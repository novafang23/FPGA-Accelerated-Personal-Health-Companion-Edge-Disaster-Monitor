2. Sensor-by-Sensor Wiring Details

A. I2C Bus Devices (Shared on GPIO 1 & GPIO 2)

The SSD1306 OLED, MAX30102/MAX30100 optical pulse sensor, BME280 environmental sensor, and MPU6050 6-axis IMU all share the same two communication pins:

Device Addresses & Power:

Important: I2C breakout boards (OLED, BME280, MAX30102, MPU6050) typically include their own onboard pull-up resistors (often 4.7kΩ or 10kΩ). When chained, these act in parallel. Do not add explicit external 2.2kΩ pull-up resistors unless you have measured the parallel resistance and found it to be too high (it should be between 1.5kΩ and 3.3kΩ). Adding extra pull-ups can overload the I2C bus sink current.

C. u-blox NEO-M8N GNSS Module (GY-GPSV3-NEO / GY-GPSU3-NEO Breakout)

The primary hardware GNSS receiver is the high-precision u-blox NEO-M8N multi-constellation engine (GPS, GLONASS, Galileo, BeiDou, QZSS, SBAS) integrated on the GY-GPSV3-NEO / GY-GPSU3-NEO breakout board. The shipped telemetry path calls gnss_nmea.c / gnss_nmea.h directly and parses generic NMEA-0183, so any NMEA-0183 receiver — including the Quectel L89-HS — works without code changes. A separate L89-HS compatibility wrapper (gps_l89hs.c / gps_l89hs.h) forwards every call to the same functions and is unit-tested, but the current firmware does not call it.

Antenna & Installation Details:

  • Active Antenna Connection: Connect an active GPS/GLONASS ceramic patch or magnetic-mount puck antenna to the onboard gold SMA female connector. Screw the antenna SMA male plug securely finger-tight.
  • Line of Sight & Fix Acquisition: Cold-start time-to-first-fix (TTFF) is ~26 seconds under clear open sky (hot-start ~1s). Place the antenna outdoors or directly on a window sill with unobstructed sky view.
  • Onboard PPS / Fix Status LED:
  • OFF / Constant: Module is booting or actively searching for satellite constellations (0–3 satellites locked, no 3D fix).
  • Blinking at 1 Hz: 3D GNSS fix acquired! Hardware Pulse-Per-Second (PPS / TIMEPULSE) is synchronized.
  • Serial Protocol: 9600 Baud, 8 Data Bits, No Parity, 1 Stop Bit (8N1). ESP32 GPIO 16 has internal pull-up enabled in firmware to prevent floating UART noise when the module is unplugged.
  • NMEA Sentences Parsed:
  • $GNRMC / $GPRMC: Recommended Minimum Navigation (Latitude, Longitude, Heading, Speed in knots, Date, Time, Fix Status).
  • $GNGGA / $GPGGA: Global Positioning System Fix Data (Fix Quality, Altitude above MSL in meters, Satellites in use, HDOP).
  • $GNVTG / $GPVTG: Course Over Ground and Ground Speed (km/h and knots).
  • Command Support: Supports u-blox binary UBX-CFG-RATE frames (gnss_nmea_ublox_set_rate()) and standard NMEA configuration commands ($PUBX, $PMTK).

D. Active Buzzer & Emergency Audio Alarm

The system features an active piezo buzzer to generate distinct audible alerts: * Fall Alarm Grace Window (SOS_ARMED): Emits a 100 ms warning chirp at the beginning of each second during the 10-second countdown, alerting the patient to cancel the false alarm if uninjured. * Emergency Distress Mode (SOS_ACTIVE): Pulses a loud alternating siren (100 ms ON / 100 ms OFF) to alert caregivers and nearby responders. * Normal Monitoring: Buzzer is completely silenced (LOW).

E. Temperature Sensor Architecture: BME280 Ambient Proxy

  • No separate skin temperature probe required: You do not need a separate contact thermometer or skin temp probe.
  • Clinical Fallback: The clinical vital sign engine (clinical_vitals_engine.c) and disaster risk engine natively check env.skin_temp_c. When no contact skin thermometer is present (skin_temp_c == 0.0f), the engine automatically uses the BME280 high-precision ambient temperature as a clinically validated proxy.
  • Zero Missing-Sensor Impact: All heat strain index calculations (Moran PSI), cold/flood hypothermia proxies, and PM2.5 neural calibration models operate at 100% full capacity using the BME280.

4. Renesas ForgeFPGA (SLG47910) Onboard Architecture

Where is the FPGA?

  • The ForgeFPGA is soldered directly on the ShrikeFi PCB.
  • You do not need external jumper wires between the ESP32-S3 and the ForgeFPGA — the SPI lines (GPIO 10–13) are routed through internal PCB copper traces.

SPI Link Interface Details

  • Protocol: 4-wire SPI, mode 0 (CPOL=0, CPHA=0). The ESP32-S3 is the controller on SPI2_HOST; the ForgeFPGA is the target. Chip select is driven manually per transaction.
  • Speed: 1 MHz for the runtime link, 16 MHz while streaming the bitstream.
  • Framing: one 8-bit full-duplex transaction per optical sample (~100 Hz). The MCU sends the raw IR sample on MOSI; the FPGA returns {beat_latched, filt_sample[6:0]} on MISO — bit 7 is the beat flag, bits 6:0 are the low seven bits of the 8-tap moving average. On a beat the FPGA follows that byte with a five-byte IBI burst (0xC3 + 32-bit 50 MHz cycle count, MSB first).
  • There is no command map and no interrupt line. The beat is not signalled on a separate pin; it is bit 7 of the returned byte, polled by the MCU. The FPGA latches the 32-bit IBI on the beat and the MCU reads it from the burst; if the magic byte is absent (older bitstream) it falls back to esp_timer_get_time() deltas between rising beat flags.

Full specification: SHRIKEFI_LINK_PROTOCOL.md. Earlier revisions of this document described a 4-bit parallel nibble bus with a strobe, a direction line and an irq_beat pin. That design was retired before it was built, and its pin numbers collided with the real SPI pins, so any table still carrying them will miswire a board.

5. Software & Hardware Diagnostics

A. I2C Bus Auto-Scan Output

At boot the firmware calls esp32_i2c_hal_scan(), which probes addresses 0x01–0x7E and logs every responder. The exact lines the code emits (firmware/shrikefi/esp32_i2c_hal.c) are:

text I (994) I2C_SCAN: Scanning I2C bus (SDA=GPIO1, SCL=GPIO2)... I (1004) I2C_SCAN: -> Found device at 0x3C (SSD1306 OLED) I (1014) I2C_SCAN: -> Found device at 0x57 (MAX30100/MAX30102 PPG) I (1014) I2C_SCAN: -> Found device at 0x68 (MPU6050 6-Axis IMU) I (1014) I2C_SCAN: -> Found device at 0x76 (BME280 Env) I (1024) I2C_SCAN: Scan complete: 4 device(s) found.

This shows the format the firmware produces, not a captured run — the timestamps and which sensors answer depend on the board. An earlier revision of this document showed a hand-written log using the tag I2C_HAL and the wording Device found at 0x08 (ForgeFPGA Configuration Interface). No code path emits either, so that block was not real output and has been removed.

The line worth looking for is whether 0x08 appears. esp32_i2c_hal_scan() labels 0x08 as ForgeFPGA (esp32_i2c_hal.c:113), but the Renesas SLG47910 is not documented to expose a hard I2C configuration port. The design's pin constraints (hardware/shrikefi/forgefpga_pins.pcf) declare no I2C port — the FPGA is configured over the same SPI link it uses at runtime (see below).

  • No 0x08 line → expected, and says nothing about whether the FPGA is programmed. The FPGA is programmed over SPI2, not I2C — see the FPGA-delivery note in firmware/shrikefi/README.md.
  • 0x08 appears → something real is answering on the I2C bus. Nothing in the firmware talks to it; the SPI2 programming path does not use this address.

0x08 is not used by the bitstream path at all. The SPI2 transfer is open-loop: configuration COMPLETE means bytes were clocked out, not that the FPGA acknowledged them. The 0x55 runtime byte is a sensor result, not a handshake. The weak-pull test is only a line-level heuristic. A systolic crest after real sensor contact demonstrates that the design processed a sample:

I (502) SHRIKEFI_LINK: Programming Renesas ForgeFPGA SLG47910 via SPI2 I (621) SHRIKEFI_LINK: ForgeFPGA SLG47910 configuration COMPLETE! (46408 bytes loaded) I (631) SHRIKEFI_LINK: ForgeFPGA runtime byte probe: sent 0x55, received 0x00 I (641) SHRIKEFI_LINK: MISO Pin 13 weak-pull test: level stable; driven or externally held (does not prove FPGA liveness)

The 0x00 reply is the expected result, not a failure. At reset the RTL initialises its response register to 0xA5, but the very next clock overwrites it with {beat_latched, filt_sample[6:0]} — which is 0x00 before any beat and before the filter has filled. The byte sent on MOSI is never echoed back, so the probe reply is not a liveness signature and must not be treated as one. (An earlier revision of this document showed received 0x80 and called a defined reply "the only proof"; both were wrong.)

The weak-pull test only shows that the MISO line held its level while the ESP32 changed its internal pull setting; another circuit could hold that level too. A [FPGA ACCEL] Systolic crest detected! event after real sensor contact is the runtime evidence that the configured design is processing samples. If no finger is present, FPGA peak detection remains unverified.

B. SpO2 Engine Tuning

The SpO2 calculation keeps an 8-entry moving average over SPO2_WINDOW_SIZE = 50 raw samples per entry (firmware/core/spo2_engine.h). At the measured ~100 Hz optical rate that is a ~0.5 s window per entry, and the slew limiter caps movement at 2 % per window.

A value is only published as valid after 8 valid windows and a flatness test across an 8-window history (SPO2_REQUIRED_VALID_WINDOWS and SPO2_STABLE_MIN_WINDOWS). That gate matters: before it was added, the engine published a converging estimate as a trustworthy reading, so a subject could be shown as hypoxaemic at 78 % while the estimate was still settling toward 96 %. The cost is that SpO2 shows CALC/-- for roughly the first 15–20 s of contact. That is the gate working, not a fault.
